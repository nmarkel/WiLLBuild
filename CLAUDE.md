> **socket = centre of the terminal downward-open bore, + 0.0917 m stem insertion**

Find the bore as the **lowest face in the outer half of the reach**, never the extreme vertex — that one change of feature is the whole fix. **FR2 crossarm: two fixtures, and it sits on the pole (0.12, Nick 8/11).** Three defects, one root cause shared with SS/AR — *the extreme feature is not the mounting feature*. (1) FR2's socket `[0.62, 0.30]` was derived from the arm's furthest geometry, which on this part is the **decorative end finial**; the real fixture tenons are upward columns at **x = ±0.4572**, so the TEX composited 16 cm outboard. **A tenon socket seats at the tenon's BASE, not its top** (Nick, 8/11): the fixture's base is a *sleeve that slides down over* the tenon, so the socket — where the fixture's origin, its sleeve's bottom rim, lands — is the host's top face the sleeve comes to rest on. FR2's tenons top out at y = 0.4191 but the crossarm's top face is **y = 0.3175**, a `0.1016 m` (4.000", standard) exposed tenon; seating at the top left every TEX standing exactly 4" proud. This holds because the sleeve is DEEPER than the tenon is tall — TEX's bore measures y 0..0.121 — so the tenon never bottoms out inside it. **A fixture whose sleeve were shallower than its tenon would instead seat at `tenonTop − boreDepth`**, and that case is not asserted (parsing TEX's 21 MB GLB per run to prove a negative isn't worth the suite time). Note this is the mirror image of the pendant rule, where the arm's bore swallows the fixture's stem (0.0917 m insertion) — same joint, opposite genders. **`direct-mount` looks like the same perch and was deliberately NOT changed:** it is a pseudo-part with `realCad: false`, so its 0.08 m stub is schematic and there is no ground truth to seat against — guessing one is the very error being fixed here. (2) FR2 is **"Fixed 2 @ 180 deg, finial"** in `docs/ordering-matrix.json` and its CAD is symmetric (x −0.611..+0.610), but only ONE fixture ever drew — `attachSocket` returns the FIRST matching socket, so the second tenon rendered bare no matter what the catalog declared. New `attachSockets` (plural) fixes the carry side; `attachSocket` stays for the mount side, where a part really does attach to exactly one host socket. **This is NOT the radial multi-arm mechanic** — that repeats a whole ARM around the pole, which on a crossarm would draw the crossarm, finial and all, twice on itself. (3) The arm floated **8.9 cm** off the pole: FR2 is the only arm whose GLB origin is not its lower attachment point (y=0 is the tips of the finials that hang BELOW the bar, leaving its pole collar at 0.0889), violating `ASSETS.md`. Corrected by a new catalog `mountOffset`, applied at the mount so the arm's own sockets stay in the GLB's native frame — a number measured off the CAD goes straight into the catalog with no rebasing. **The arguably-more-correct fix is a translate at ingest in `real-parts.json` next to `rotateY`** (it would make the asset obey ASSETS.md instead of compensating for it); it was not taken because it moves the rig's recorded anchor and so needs the part re-rendered, and the rig's devDeps aren't installed. Two fixtures on one arm also needed depth ordering — `offsetDepthProxy` generalizes `armDepthProxy` (proved equal for an arm reach in `composite.test.ts`) so the far fixture draws BEHIND the crossarm. **CR2 is the same "Fixed 2 @ 180 deg" product and still has one socket on purpose:** it's on a single-ended placeholder tube, so a second socket would composite a fixture onto an end its artwork doesn't have — bump it with its real CAD, not before. **Open, deliberately not invented:** the quote/summary still lists the fixture once, though an FR2 build ships two.

## Core architecture rules

1. **All catalog knowledge lives in `public/catalog.json`.** Components never hardcode part lists, socket offsets, or compatibility logic.
2. **The current selection is a single serializable `config` object** — it later becomes the platform's structured config JSON, so keep it clean:

```json
{
  "configId": "uuid",
  "pole": "alum-pole-20",
  "baseCover": "bc-fluted",
  "arm": "sh1-shepherds-hook",
  "fixture": "gvx-pendant",
  "finish": "matte-black",
  "rev": 1
}
```

3. **Compatibility = socket matching only.** Each part has `mount` (what it attaches to) and `sockets` (what it carries). Selection order is fixture-first (`SLOT_ORDER` in `src/lib/compat.ts`): Fixture → Arm → Pole → Base Cover → Finish. Socket rules: post tops (DRX/TEX) mount `tenon-2-3/8` (direct pole mount, crossarms, bullhorns, supported arms — NOT the upsweep, which is arm-mount only per H3b), GVX Pendant mounts `pendant` (pendant arms, shepherd hooks, suspension brackets), MVX Coach mounts `arm-mount` (upsweeps). Rules live in catalog socket data, never component code. Filter the UI so invalid combos are unselectable — never render a broken assembly.
4. **Catalog part shape:** `id`, `slot` (pole|baseCover|arm|fixture), `name`, `family`, `heightFt`/`dims`, `sockets`, `compatibleSockets`, `finishes[]`, `keywords[]` (describe-box matching; finishes have them too), `model` (GLB path), `thumbnail`, `productUrl` (real willbrands.com page). Catalog root also has `finishesProvisional: true` (WiLLcoat palette unconfirmed — flagged in the Finish step UI) and `referenceAssemblies[]` (drives the Standard/Configurable status chip).
5. **In-house products only.** Fixtures: DRX Post Top & Area, TEX Post Top & Area, MVX Coach, GVX Pendant. Arms: SH1 Shepherds Hook, Decorative Upsweep, PA1/PM1 Pendant Arms, plus a "Direct Pole Mount" tenon-adapter pseudo-arm. Poles: WiLLstudio Decorative Aluminum (8/10/12/14/15/16/18/20 ft, ids `alum-pole-NN`). Base covers (0.10.5: the five official designs, replacing the earlier curated fluted/round): CL1/CL2/CL3 clamshells (small/medium/large), SC1/SC2 spun collars.
6. **Don't block on assets.** The viewer never renders geometry at runtime. Every part shows a pre-rendered image layer (interim: rig renders of the placeholder solids; final: Cole's SolidWorks renders into the same manifest slots). Missing render → labeled "Preview render coming" fallback, never a broken viewer.

## Compositing viewer requirements (0.5 — replaces the old 3D scene)

- **Assembly products:** stack transparent WebP layers in z-order (pole < baseCover < arm < fixture) from `resolveAssemblyLayout`. Layers align because every layer is rendered against ONE shared rig (fixed ortho camera/lighting/scale) and positioned by projecting catalog socket offsets through the rig's `worldToImage` map — no hardcoded offsets, same socket walk as the old 3D assembly.
- **Standalone products:** one hero render (`resolveRenderAsset`). Asset model is keyed by angle (`angles.hero`) so front/45°/side can be added later; one hero angle ships now (no free orbit — deliberate tradeoff).
- Finish swap = swap the layer set for that finish id (instant; all 13 finishes pre-rendered per part, per part slot — 0.10.5 made finish per-component).
- **Render-scope rule (spec D9 — NO exemptions; angle set narrowed in 0.11 E):** every catalog part ships all 4 canonical angles (`hero`/`az90`/`az180`/`az270`) × all 13 finishes, whether rig-rendered from a placeholder solid or from real CAD. `src/lib/composite.coverage.test.ts` enforces this against the live catalog + manifest, and additionally fails on a *stray* angle outside the set so a retired angle can't linger in the bundle. A part shipping a partial set is a bug to fix, never something to special-case — the former `REAL_RENDER_PARTS`/`CORE_FINISH_IDS` carve-out is gone and stays gone. **The angle list is duplicated in three places that must move together:** `COMPASS` in `scripts/render-rig/generate.mjs`, `RENDER_ANGLE_KEYS` in `src/lib/composite.ts`, and `COMPASS` in the coverage test (which imports the constant rather than re-listing it).
- **Canonical view set (0.11 E + the 0.10.5_TO merge):** the carousel `ASSEMBLY_VIEWS` — Assembly at `viewYaw` ∈ {0, 90, 180} (`ASSEMBLY_VIEW_YAWS`, `snapAssemblyYaw` = nearest by circular distance) plus the `poleTop`/`poleBottom` composite focuses (`focusBox`/`availableViews`). `FOCUS_TARGETS` still carries the single-slot `fixture`/`arm`/`baseCover` targets — `focusBox` supports them and they're unit-tested, but no carousel stop offers them, so `currentViewIndex` returns -1 and the headline reads "Custom view". Focus views are viewer FRAMINGS over the composited layers, never new assets — the rig alpha-crops each part individually, so re-rendering one part "tighter" produces the identical image. **Adding the 90° view cost zero renders**, and that is a property, not a coincidence: the required azimuth set is `(armAzimuth + armOrientation − viewYaw) mod 360`, which stays `{0,90,180,270}` for any view set whose members are multiples of 90 — asserted in `composite.test.ts` ("adding a view cannot require a new render azimuth"), so widening the view set again is safe only while that test passes. The 4 render azimuths exist because a radial cluster shows arms four ways inside ONE view, which is a different thing from the number of views. A projected ground-compass ring at the pole base tracks the arm arrangement's own 0/90/180/270° orientation independently.
- **Rail ↔ viewer coupling:** picking a part frames it (`selectAndFrame` in `Panel.tsx`: fixture/arm → Pole Top, baseCover → Pole Bottom, pole → assembly), and clicking a viewer callout scrolls that rail section into view (`onSlotClick` → `builder-step-<slot>`). The assembly-change reset in `CompositeViewer` clears the CAMERA only — it must never reset `focus`/`viewYaw`, or it clobbers the focus the rail just set and the headline flicks back to "Assembly (0°)".
- **Pan clamping is per-scene:** Blank/studio clamps (product can never get stuck off-screen); photo scenes allow FREE placement so the product can be posed in the photo. The `clamp` flag must travel in `clampBaseRef`, not just gate the render expression — the pointer handlers call `currentEffPan()` mid-gesture, and a still-clamping version snaps every free drag back on pointerup.
- Night view (conceptual, labeled "not a photometric simulation"), ~1.83 m human-scale silhouette overlay, and image zoom carry over from the 3D viewer. Orbit is gone.
- Real units: the rig renders at 1 world meter = `rig.pxPerMeter` px (360 as of 0.10.5); the app never re-derives camera math — it consumes `worldToImage`/`pxPerMeterY` from the manifest.
- Asset generation lives entirely in `scripts/render-rig/` (offline, devDeps). Catalog knowledge stays in `public/catalog.json` + `public/renders/manifest.json`; components never hardcode offsets.

## Asset pipeline

Document in repo as `ASSETS.md`. CAD (STEP/SolidWorks) → Blender → GLB:

1. Decimate to visual quality (target < 500 KB per part with Draco)
2. Origin at the part's lower attachment point; +Y up
3. Named empty nodes for sockets: `socket_top`, `socket_arm`, `socket_fixture`
4. Single material slot named `finish` on paintable surfaces
5. Export GLB with Draco compression
