## Problem

Two branches diverged from `Dev` (7837c23, = `phase-0.9`) and each rewrote the same eight
frontend files. They are siblings, not a chain — neither contains the other's work.

| | `phase-0.10` (cd587f7) | `phase-1.0-concierge-config` (31c95c6) |

| Commits | 1 (squashed) | 20 |

| geometry-service | 17 files changed | **untouched** |
| Catalog | +539 lines | +6,657 lines; parts 108 → 117; finishes 5 → 13 |
| Renders | 1,221 files / 2.8 MB | 7,997 files / 27.6 MB |
| Frontend health | — | `tsc` clean, 308/308 vitest pass |
| Service health | — | **68 failed, 85 errors** (129 × `unknown slot: 'standalone'`) |

The root cause of the divergence: `phase-0.10` was never merged to `Dev`, so Tyler branched
from a `Dev` that lacked it.

## Naming

The combined branch is **`phase-0.10.5`** — "0.10 plus Tyler's independent work", sitting
between 0.10 and 0.11 in the established `0.N` sequence. `phase-1.0-concierge-config` skipped
a full major version; nothing in the project is at 1.0.

`Phase 0.11 — Per-Component Finish, Taxonomy & Viewer Polish` already exists in the vault
(dated 2026-08-04) and is **unclaimed**. Tyler's branch was his own initiative, not an
implementation of that spec; the two overlap because Tyler was the source of the Round 5
feedback the spec was written from. Naming this branch `0.11` would wrongly mark that spec
delivered, so 0.10.5 keeps 0.11 live.

The rename is total: branch name, ~40 in-code `Phase 1.0` / `Phase 1.1` comment references →
`Phase 0.10.5`, plus `CLAUDE.md`, `ASSETS.md`, and docs. Tyler's 20 individual commit messages
are **not** rewritten — that would destroy authorship attribution. The rename lands as its own
commit on top, so `git log` shows the correction rather than pretending 1.0 never happened.

Both source branches stay pushed and untouched as the audit trail. Delete only after 0.10.5
merges to `Dev` and is proven.

#### Real-CAD-first rule (D8)

The rig must never render a placeholder solid for a part that has real geometry available, and
where the two branches disagree about which file backs a part, **the source STEP decides**. Two
concrete corrections fall out of this: `bc-cl2-medium-clamshell` comes from `CL2-4R.STEP` (not
`bc-round.glb`, which is CL1), and `mvx-coach` returns to real geometry instead of the
placeholder Tyler left it as.

Add an assertion to the rig: if a part appears in `real-parts.json` and its GLB is present, a
placeholder render for that part is a hard failure, not a fallback.

#### Pole scaling (D10)

`RSAA-4040-12.STEP` is the only real pole, but poles are straight extrusions, so scaling it
along its axis to 8/10/14/15/16/18/20 ft carries the real profile, wall thickness and hand hole.
Record each derived pole in `docs/real-geometry.json` with `kind: "derived"` and its source file
+ scale factor, so a scaled pole is never mistaken for a native export.

After this, **23 of 117 parts** are backed by real or real-derived geometry (14 existing GLBs minus the 3 stale mis-mapped covers, + 5 new base covers + 7 scaled poles), up from 9 on Tyler's branch and 14 on 0.10.

#### Render scope (D9)

Every one of the 117 parts gets all 8 angles × all 13 finishes — **no exemptions**, standalone
products included. That is 12,168 manifest entries, 36.5 MB of tracked assets (up from 7,974 / 27.6 MB). This is the count 0.11's Workstream E asked to have confirmed before committing;
it is confirmed here.

**Measure before estimating:** render one part first to get real throughput, then multiply. The
target is 12,168 entries versus 7,974 today, so expect roughly 1.5× the last full run. Do not
commit to a wall-clock estimate before measuring.

Tyler's skip-guard (preserve the stale manifest entry when a GLB is absent) stays in place as a
safety net, but under D8 it should now be **loud**: every skip must be logged and summarised at
the end of the run, because on this machine a skip means something is wrong rather than
expected.

#### Manifest gaps this re-render closes

Audited 2026-08-06. Every gap is a real-CAD part whose GLB was absent on Tyler's machine, so
his skip-guard preserved a stale entry. **All 14 GLBs are present on this machine**, so the
re-render closes all of it:

| Part | Gap | Silent consequence today |
|---|---|---|
| `gvx-pendant`, `sh1-shepherds-hook` | 5 of 13 finishes; angles stuck on retired `az120`/`az240` set | — |
| `willstudio-side-shepherds-hook-pole-top-brackets`, `willstudio-suspension-arm-pole-top-brackets` | 10 of 13 finishes; same retired angle set | — |
| `alum-pole-12`, `bc-cl2-medium-clamshell`, `bc-round` | 5 of 13 finishes | — |
| `willstudio-cr2-decorative-crossarm` | `az315` block has **zero** finishes | Outright hole, masked by `nearestAngleKey` |

Two consequences, both currently invisible to the test suite:

1. **Per-component finish silently substitutes on the real-CAD parts.** Choosing e.g.
   `light-gray` on an SH1 arm hits `resolveRenderAsset`'s "first available finish" fallback and
   renders a different color — on exactly the parts that look best.
2. **The 8-position rotation degrades to 4.** `resolveAssemblyLayout`'s `supports45` check sees
   any part lacking `az45` and snaps the whole assembly to 90° steps. Since GVX, SH1 and both
   bracket arms are affected, this hits most WiLLstudio assemblies.

`composite.coverage.test.ts:34` deliberately exempts `REAL_RENDER_PARTS` to `CORE_FINISH_IDS`
(5 finishes) with an honest comment about GLBs living only on the owning machine — which is why
308 tests pass through all of the above. **After the re-render, delete that exemption** and
assert the full D9 matrix: all 13 finishes × all 8 angles for all 117 parts, with angle
resolution asserted **exact** so `nearestAngleKey` fallbacks can no longer mask a hole.

That also lets `resolveAssemblyLayout`'s `supports45` degradation path become dead code for the
shipped manifest. Keep the function — it is correct defensive behaviour if a future manifest
regresses — but add a test asserting that the *shipped* manifest never triggers it, so the
8-position rotation cannot silently drop to 4 again.

Regenerate `public/renders/manifest.json` via `npm run render-manifest`, then
`node scripts/build-viewer-assets.mjs` for `viewer-assets.md`.
